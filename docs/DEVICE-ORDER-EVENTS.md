# Общие события и история заказов POS

Локально подготовлено13.11.2026. Новые read-only маршруты монтируются перед публичным `/api/orders/:token`. Старые Web, accept/ready/status и Telegram-обработчики не меняются.

## API

Оба GET требуют существующий `X-Device-Key` активного устройства через `requireDevice`, возвращают `Cache-Control: no-store`. Доступ общий для касс одного развёртывания/одной организации; секрет не передаётся в query. В ответах нет tracking_token.

- `GET /api/orders/current` → `{orders:[…],complete:true}`. Полный список новых неоплаченных заказов, максимум1000. При превышении —409/CURRENT_QUEUE_TOO_LARGE без частичного списка. Ошибка БД —503, не успешный пустой ответ. Приложение заменяет inbox только по подтверждённому полному ответу.
- `GET /api/orders/history?limit=5&cursor=…` → `{orders:[…],nextCursor:string|null}`. По умолчанию5, допустим1–50; Android всегда запрашивает5. История включает все статусы. Сервер читает limit+1 для проверки следующей страницы. Порядок `(created_at DESC,id DESC)`, keyset без OFFSET. Курсор version1/base64url содержит точную PostgreSQL дату с6микрознаками иUUID, параметры SQL передаются отдельно. Новый заказ не сдвигает уже читаемые страницы.

Записи содержат номер/id, status, customer_name, phone, address, comment, total, delivery_fee/тариф, created_at/updated_at, web_paid_at и order_items. `web_paid_at` позволяет показывать оплату, не подменяя базовый статус заказа. Отменённый заказ отображается отменённым. Возврат native-чека не создаётся этим API и не считается отдельным серверным статусом возврата.

## Без побочных действий

Маршруты выполняют только SELECT. Они не принимают заказ, не создают чеки, не списывают товары, не вызывают Telegram/печать и не привязывают заказ к конкретной кассе. Смена статуса во время просмотра видна при следующем обновлении. Гонка одновременного принятия двумя кассами не решается новым read-only API.

## Развёртывание — отдельно по команде владельца

1. Выполнить очередную миграцию `016_device_order_history.sql` штатным Flyway-процессом. Она добавляет индексы общей истории/новых заказов; не изменяет существующие записи.
2. Обновить backend с `device-order-events.js` и импортом/регистрацией в `server.js`.
3. Установить новую native-версию. API использует тот же URL/key и базовый ordersPath.
4. Проверить на двух тестовых кассах: заказ появился на обеих; первая приняла; после «Обновить» на второй он ушёл из текущих и виден в истории как принятый. Проверить5/10/15записей, отменённые/оплаченные и отказ доступа.

Публикация выполняется штатным Deploy to VDS: Node22 tests → Flyway/PostgreSQL integration → deployment с применением миграций → проверка SHA/health. Применение016 подтверждается журналом конкретного успешного deployment, а не наличием этого файла. Проверки новых маршрутов без ключа должны давать401; реальные заказы ради тестирования не изменяются.
