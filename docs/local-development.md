# Локальная разработка на macOS Apple Silicon

Проект запускается с Node.js 22 и отдельным PostgreSQL 17. Docker не требуется.
Нужен установленный PostgreSQL 17; по умолчанию используются бинарники Homebrew
из `/opt/homebrew/opt/postgresql@17/bin`. Другой путь задаётся через `MPOS_PG_BIN`.

Из корня репозитория:

```bash
bash scripts/local-dev.sh setup
bash scripts/local-dev.sh start
```

`setup` скачивает Node.js 22.23.4 с проверкой SHA-256, выполняет `npm ci`, создаёт
локальные пароли, отдельный кластер и базу `mpos`, применяет все `db/migrations/*.sql`.
Повторный запуск сохраняет данные и проверяет контрольные суммы применённых миграций.
Новые миграции применяются через `bash scripts/local-dev.sh migrate`.
Этот локальный runner не заменяет Flyway при развёртывании на VDS.

- Сайт: <http://127.0.0.1:3000/>
- Меню: <http://127.0.0.1:3000/menu/>
- Проверка процесса: <http://127.0.0.1:3000/health>
- API меню с обращением к БД: <http://127.0.0.1:3000/api/menu>
- PostgreSQL: `127.0.0.1:55432`, база `mpos`, роль приложения `mpos_app`.

`start` запускает сервер с `--watch`: изменения модулей перезапускают Node.
HTML/CSS/JS из `public` подхватываются при обновлении страницы.

```bash
bash scripts/local-dev.sh status
bash scripts/local-dev.sh test
bash scripts/local-dev.sh stop
```

Конфигурация приложения и пароль БД находятся в игнорируемом `.env.local`.
Кластер БД, Node.js, фото товаров и логи — в игнорируемом `.local/`.
Логи: `.local/backend.log`, `.local/postgres.log`.
После изменения `.env.local` выполните `stop`, затем `start`.
`stop` сохраняет данные; после перезагрузки компьютера выполните `start`.

База создаётся пустой: рабочие товары, фотографии и заказы сюда не копируются.
Для 24 тестовых товаров в 6 категориях с локальными SVG-иллюстрациями и остатками
выполните `bash scripts/local-dev.sh seed`. Повторный запуск не создаёт дубликатов.
Скрипт использует только локальную базу на порту 55432 и отказывается добавлять
второй активный POS. Две позиции имеют нулевой остаток, кофе — без ограничения количества. Ключи и токен рабочего Telegram-бота не используются;
проверка телефона и отправка уведомлений требуют отдельной тестовой интеграции.
API и PostgreSQL слушают только loopback. Изменения в GitHub автоматически не отправляются.


## Личный кабинет

Страница: <http://127.0.0.1:3000/account/>. Иконка есть в навигации меню и онлайн-заказа.
История заказов и бонусы пока представлены макетом с пометкой «Скоро».

Миграция `009_customer_account.sql` добавляет одноразовые запросы входа и сессии.
Миграция `010_account_phone_from_telegram.sql` разрешает неизвестный номер у ожидающего
подтверждения. POST `/api/account/start` не принимает номер и возвращает ссылку существующего формата
Telegram `?start=<token>`. Страница сразу переходит по этой ссылке. Бот использует существующий защищённый
POST `/api/phone-verification/:token/confirm`, проверяет принадлежность контакта
Telegram-пользователю, проверяет полный номер +375 и предлагает вернуться по `returnUrl`
на `/account/`. Backend также независимо проверяет +375 и 9 цифр.
Исходная вкладка также проверяет подтверждение, пока она видима.

POST `/api/account/complete` принимает только HttpOnly cookie запроса входа;
после подтверждения выпускает HttpOnly SameSite=Lax cookie `mpos_account` на 90 дней.
В production cookie имеет Secure, в БД хранится только SHA-256 случайного токена.
GET `/api/account/session` возвращает профиль, POST `/api/account/logout` отзывает сессию.
POST-маршруты проверяют Origin и JSON Content-Type. Запрос входа живёт пять минут.

Ключи рабочего бота не используются. Пока `OWNER_BOT_SHARED_SECRET` не настроен,
начало входа возвращает понятную ошибку 503. Для живого теста нужен отдельный
тестовый бот с `TELEGRAM_BOT_USERNAME`, общим `OWNER_BOT_SHARED_SECRET` и доступным ему
callback backend. Локальная копия Telegram-бота находится рядом, в `../project_bot`, ветка
`dev/account-telegram-login`. В ней добавлены строгая проверка +375 и кнопка возврата
на разрешённый origin `ACCOUNT_SITE_URL`. Для production оба репозитория развёртываются из `main`: сначала backend
с миграциями, затем существующий сервис бота. Живое прохождение требует согласованных
настроек shared secret и URL.
На удалённом боте `127.0.0.1` указывает на сервер бота: напрямую достучаться до локального
API он не может. Для интеграции нужен доступный тестовый backend или согласованный туннель.
Не запускайте второй polling-процесс рабочего бота.


## Кабинет участника

Миграция `011_customer_account_profile.sql` добавляет добровольно заполненные имя,
дату рождения и адрес доставки. PATCH `/api/account/profile` принимает только эти поля;
номер берётся из действующей сессии и не меняется через форму.
GET `/api/account/session` связывает подтверждённый телефон с карточкой клиента POS,
проверяет действующее участие и возвращает активные акции с реальными балансами
из `loyalty_balance`. Числа и названия не зашиты в интерфейс; при отсутствии участия
показывается пустое состояние без автоматического согласия.
GET `/api/account/orders` возвращает последние 30 онлайн-заказов только этого номера/клиента.
POS-чеки, которые не передаются в backend, в эту историю не входят.
GET `/api/account/qr` генерирует SVG с подтверждённым телефоном, без токена авторизации.
Это идентификатор номера, не разрешение на использование подарка; обработка сканирования
в конкретной кассе требует поддержки QR в клиенте POS. Телефон остаётся видимым рядом.
Все account-ответы имеют `Cache-Control: no-store`; изменение профиля защищено Origin/JSON.
Для просмотра мобильной вёрстки используйте только отдельный синтетический локальный аккаунт.
Тестовые имя, дата и адрес на скриншотах не являются значениями по умолчанию для пользователей.


## Подарки и данные при заказе

Общая карточка `loyalty-cards.js/css` показывает прогресс; доступный подарок получает
анимацию свечения и блика с учётом reduced motion. Она используется в кабинете и корзине.
Корзина показывает только доступные подарки, подтягивая текущий account session при открытии.
Имя и телефон заполняются для самовывоза и доставки; ручные правки не затираются.
Это отображение доступного подарка, без автоматического списания баланса или изменения цены заказа.
QR-блок помечен «Скоро» и слегка размыт. Сбор даты рождения отключён в интерфейсе и API;
миграция `012_remove_account_birth_date.sql` удаляет колонку и прежние значения после выкладки совместимого кода. Дата рождения больше не принимается, не возвращается и не хранится в рабочей схеме.
